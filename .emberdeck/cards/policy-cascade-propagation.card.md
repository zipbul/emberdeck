## Policy

The `card.key` column is the foreign key parent for all child tables: `card_keyword`, `card_tag`, `card_relation` (both src and dst), `code_link`, and `card_changelog`. All foreign keys are declared with `ON DELETE CASCADE` and `ON UPDATE CASCADE`.

## Consequences

- **Delete**: deleting a card row automatically removes all its keywords mappings, tag mappings, relations (both outgoing and incoming from other cards), code links, and changelog entries. After cascade, `pruneOrphans` cleans up keyword/tag rows that are no longer referenced by any card.
- **Rename**: updating `card.key` automatically propagates the new key to all child rows. This is why `renameCard` uses a raw SQL `UPDATE card SET key = ?` instead of delete+insert -- it preserves all incoming relations from other cards.

## What breaks if violated

- If CASCADE is missing on delete, orphan rows accumulate in child tables, wasting storage and corrupting queries (e.g., `findByCardKey` returns relations to deleted cards).
- If CASCADE is missing on rename, child rows still reference the old key, making them invisible to queries on the new key.
- If `pruneOrphans` is not called after delete, keyword/tag dimension tables accumulate garbage entries.

## Exclusions

- The `cardFts` (FTS5) virtual table is not managed by FK cascade. FTS sync is handled by SQLite triggers defined in migration SQL.
- `card_relation.isReverse` rows are auto-generated by the relation repository, not by FK cascade.
